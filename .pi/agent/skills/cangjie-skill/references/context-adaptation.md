# 蒸馏后的语境适配 (Context Adaptation) — 一个可选的下游模式

> 何时用: 当用户不只是要"把内容蒸馏成 skills",而是要"读了 X 之后**告诉我该怎么用在我的情况上**" —
> 即蒸馏的产物要直接服务于一个具体的决策/转型/规划任务。cangjie 主流水线产出的是通用可复用单元;
> 本模式在其后追加一层"针对当前用户语境的批判性适配",避免把一套框架**照搬**到一个它并不完全适用的现实里。
>
> 来源: 一次把 3 个 YC 视频转写稿蒸馏成 "AI-first company transition" 框架、并为用户(一家现有创意工作室)
> 定制落地路线的真实会话。

## 核心洞察

大多数商业/方法论内容都**默认一个理想起点**(常见的是"创业公司 / 白纸一张")。当用户的真实处境与该默认不符时,
直接产出的框架会在最难的地方(迁移路径、变革管理、组织现状)**留下沉默的盲区**。蒸馏做得再干净,
如果不做这一层适配,交付的就是一份"对别人正确、对这个用户误导"的文档。

## 三份文档,职责分离(关键)

不要把"内容说了什么"和"我们怎么看"混在一个文件里。产出三份交叉引用的 markdown:

| 文件 | 内容 | 署名边界 |
|---|---|---|
| `foundation.md` | 源材料说了什么(=cangjie 主流水线的 DIGEST/单元) | 忠实于源,标清出处 |
| `analysis-and-questions.md` | 我们的判断:盲区、缺失层、哪条原则不适用 | **明确标注为"我们的综合",不是"框架说"** |
| `roadmap.md` | 我们要做什么,分阶段,决策点悬挂 | 我们的决策,随决策落定持续更新 |

这样能防止"我们的观点"被误读成"权威框架的结论",作者归属始终透明。

## 适配四步

### 1. 找默认起点 (identify the assumed starting state)
问一句:"这套材料**默认**用户处在什么状态?" 常见默认 = 创业公司/无历史包袱/单一业务。
写下源材料**只字未提**的东西 —— 对现有公司来说,迁移路径和变革管理往往正是最难、却完全缺席的部分。

### 2. 逐条原则分类 (triage each principle)
对提取出的每条原则/模型,针对**当前用户**打标签:
- **免费的赢 (free win)** — 用户已天然满足(例:创始人已有 AI 动手能力 → "先建立信念"这条直接跳过)
- **仍成立 (holds)** — 照用
- **不适用 (N/A)** — 对该用户是空集(例:"干掉中层管理" 对一个 2 人团队毫无意义)
- **危险 (dangerous)** — 照搬会出事,需要改写或加防护

### 3. 补缺失层,并打标签
源材料没覆盖、但用户必需的层(迁移、变革管理、人的政治),**自己构建**,并显式标注
"这是我们的综合,不是原框架" —— 不要让自造内容冒充源权威。

### 4. 痛点 vs 框架顺序的错位检查 (pain-priority mismatch)
框架有它天然的推进顺序(例:LEARN→WIRE→AUTOMATE→SCALE);用户有他天然的**最痛点**。
两者极少重合。找出分歧,**按用户痛点重排序**(例:用户的第一痛点是"知识散落无法检索" = WIRE 层,
那就把 WIRE 提到最前,LEARN 压缩或跳过)。

## 路线图的两条附加纪律

- **以用户 #1 痛点开局**,而不是框架的天然起点。
- **把架构选择显式挂成"待用户决策"**,不要静默替用户拍板(例:知识库用 Obsidian 还是 Notion、
  本地 markdown 还是 API)。用户懂自己的技术栈,你不懂。每个阶段给出**退出判据**(可验证的"做到了"标准)。

## 与主流水线的关系

- 本模式是 cangjie 阶段 5(交付)**之后**的可选延伸,只在"蒸馏服务于具体落地任务"时触发。
- 若用户只是要一组通用可复用 skills,不需要本模式 —— 主流水线到 DIGEST + 安装即可。
- 触发词识别:用户说"读了这些**帮我看看怎么用在我的公司/项目上**""据此给我一个落地计划"而非"做成 skill 库"。
